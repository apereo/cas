Shape the CAS Screens From Theme Properties

Login, error, multifactor and consent screens gain theme properties, each previewed live in the new theme builder.

  • Identity providers move before or after the login form, in a stack, a grid or a row, with their own sort and dropdown threshold.
  • Multifactor selection, Google Authenticator, WebAuthn and consent screens choose their layout, what they show and what they recommend.
  • QR codes take their size, colors and margin from the theme, and device names can start empty, random or with the username.
  • The main content of every page can sit anywhere on a 3x3 grid, from the top left to the bottom right of the screen.

New & Noteworthy

The following items are new improvements and enhancements presented in this release.

OpenRewrite Recipes

CAS continues to produce and publish OpenRewrite recipes that allow the project to upgrade installations in place from one version to the next. See this guide to learn more.

Graal VM Native Images

A CAS server installation and deployment process can be tuned to build and run as a Graal VM native image. We continue to polish native runtime hints. The collection of end-to-end browser tests based on Puppeteer have selectively switched to build and verify Graal VM native images and we plan to extend the coverage to all such scenarios in the coming releases.

Testing Strategy

The collection of end-to-end browser tests based on Puppeteer continue to grow to cover more use cases and scenarios. At the moment, total number of jobs stands at approximately 618 distinct scenarios. The overall test coverage of the CAS codebase is approximately 94%.

JSpecify & NullAway

CAS codebase is now annotated with JSpecify annotations to indicate nullness contracts on method parameters, return types and fields. We will gradually extend the coverage of such annotations across the entire codebase in future releases and will integrate the Gradle build tool with tools such as NullAway to prevent nullness contract violations during compile time.

Spring Boot 4.2

CAS is now built on top of Spring Boot 4.2.x. This is an in-progress ongoing minor platform upgrade that affects almost all aspects of the codebase including many of the third-party core libraries used by CAS as well as some CAS functionality.

Please refer to the Spring Boot Wiki for more information on the changes and updates in this release.

Theme Builder

The CAS header has a new palette button, next to the notifications button, that opens a theme builder. It lists every theme property with its description and current value, and edits the colors, shapes, font, header, footer and background that custom.css usually controls. Changes are previewed live on the page without a reload, including elements that a theme property would turn off, and the result downloads as a cas-theme-custom.properties file and a custom.css file ready for an overlay. When the builder opens on a server that already serves such a custom.css, it reads its own block back so the file can keep evolving. Nothing is saved on the server; the builder is turned on by default and is controlled by the cas.theme-builder.enabled theme property.

Theme Properties

Several screens can now be adjusted through theme properties, so they can differ per theme, per application and per tenant, and most of them preview live in the theme builder:

Screen Theme properties
Every page cas.main-content.position (topleft … bottomright, default topcenter)
Login form cas.login-form.password-reveal.enabled, cas.login-form.caps-lock-warning.enabled
Login card cas.login-side-panel.position (start, end), cas.login-providers.position (after, before)
External identity providers cas.login-providers.layout (stacked, grid, inline), .select-threshold, .sort
Password management links cas.pm-links.forgot-password.url
Error pages cas.error.show-message, cas.error.show-details
WebAuthn cas.webauthn.authentication.show-device-details, cas.webauthn.registration.recommended
Google Authenticator cas.gauth.registration.show-secret-key, .scratch-codes (chips, list), .show-print
QR codes cas.qr-code.size, cas.qr-code.foreground, cas.qr-code.background, cas.qr-code.margin
Multifactor authentication cas.mfa.selection.layout (list, grid, cards), cas.mfa.device-name.prefill
Attribute consent cas.consent.show-attribute-values, cas.consent.layout (table, list)

The main content position places the content of every page in a 3x3 grid on the screen: top, middle or bottom, and left, center or right, as in middleleft or bottomright. Pages taller than the screen still start at the top and scroll, and Palantir keeps its own layout.

Defaults keep the screens as they were, with two exceptions: external identity providers keep their configured order in the dropdown that replaces the buttons once there are more than ten, and the error page offers its details button only when cas.error.show-details is turned on, in which case it now shows the stack trace the server includes rather than an empty box. QR codes for Google Authenticator, WebAuthn and QR code login use the QR code properties of the theme that applies to the request; their size stays between 100 and 1000 pixels, and a foreground that is not darker than the background falls back to black on white so the code remains scannable. Device and account names suggested when registering trusted devices, Google Authenticator, YubiKey or WebAuthn devices can start empty, random or with the username.

Account Profile

The account profile shows more of what CAS knows about the user:

Section What it shows
Overview Days left before the password expires, from the password policy warning, with a shortcut to change it.
Sign-ins Successful, failed and risky sign-in attempts of the last 30 days from the authentication events.
Contact Email addresses and phone numbers for one-time codes and for passwordless sign-in.
Tokens Refresh tokens (offline access) next to access tokens; revoking one revokes its access tokens.
Usage policy Whether the acceptable usage policy is accepted, and the policy terms.
Impersonation Accounts the user may impersonate, and on whose behalf an impersonation session runs.
QR devices Devices authorized for QR code login, which the user can remove.
MFA devices YubiKey registration, new Google Authenticator scratch codes, renaming WebAuthn passkeys.

YubiKey registration is offered when the user has no device yet or when cas.authn.mfa.yubikey.multiple-device-registration-enabled is turned on, and an email address for one-time codes can be added when cas.authn.mfa.simple.mail.accepted-email-pattern is set.

Other Stuff

Authentication

  • JWT authentication takes the subject of a token as the principal as it is, and every other claim as an attribute. Tokens built with pac4j, whose subject carries a profile type such as org.pac4j.core.profile.CommonProfile#casuser, now sign in as that whole subject and must be issued again with a plain one. A service without a signing secret no longer accepts any token. The tokenAuth actuator endpoint no longer issues tokens: it validates one and answers the principal and the identifier, name and service id of the service, never its properties or secrets.
  • For unsolicited SSO, the SAML2 identity provider no longer signs the authentication request it builds itself, nor checks it for a signature, and the signUnsolicitedAuthnRequest setting of SAML2 service definitions is removed. Unsolicited SSO also works when the session state is kept in browser storage. Delegated authentication no longer reloads the metadata of a SAML2 identity provider for each request.

Multifactor & Passkeys

  • The Google Authenticator registration QR code includes digits and period when cas.authn.mfa.gauth.core.code-digits or cas.authn.mfa.gauth.core.time-step-size differ from the defaults, so authenticator apps generate codes CAS accepts.

OAuth & OpenID Connect

  • Front-channel logout requests now carry the same sid as the ID token and the back-channel logout token; the session identifier used to be computed differently, so applications could not match it to the session they had recorded.
  • Access tokens issued as JWTs can be revoked through the revocation endpoint, and refresh tokens issued as JWTs can be redeemed with the refresh_token grant; both used to be looked up in the ticket registry without being decoded first, so revocation silently did nothing and the refresh request was refused.
  • JWT access tokens are no longer signed with keys from the application’s own jwks that are marked for encryption ("use": "enc"); when the application publishes only encryption keys, CAS signs with its own keys. jwtAccessTokenSigningAlg is honored as documented: CAS picks a signing key whose type fits the algorithm, and the key’s own algorithm only applies when none is configured or the configured one does not fit the key. Signatures made with an EC (ES*) or RSA-PSS (PS*) key are randomized, so such a token is a different string each time it is encoded; the ID token’s at_hash is computed over the access token the response carries.
  • OAuth relying parties may request access tokens for specific resources with the RFC 8707 resource parameter, limited to the resources listed in the service definition’s allowedResources, with authorization and pushed authorization requests, device authorization and CIBA requests, and the password, client credentials, JWT bearer and pre-authorized code grants. Other resources are refused with invalid_target. Requested resources are added to the access token audience. Redeeming a code or refresh token may narrow the access token to some of the granted resources, while the refresh token keeps them all. A token exchange issues tokens for its own audience or resource only, without the resources of the exchanged token. In request objects, resource may be a single value or a list. The consent screen lists the requested resources, and a remembered consent decision covers only the resources it was given for. Resources can be defined in the Palantir service wizard.
  • The allowedResources of a service definition and of its token exchange policy are regular expressions with the same rule: every requested resource must match one of them in full, case-sensitively. The token exchange policy used to accept a request when any one of its resources was found by any pattern. A token exchange is also checked against the service’s own allowedResources when the service defines them.
  • The MCP server reports the audience and allowed resources of OAuth and OpenID Connect clients, and the new checkOidcClientResource tool tells whether a client may request a resource, which allowed expression it matches or why it would be refused, and the audience of the token.
  • Resources every client may request can be listed with cas.authn.oauth.core.allowed-resources, in addition to the allowedResources of each service. CAS allows its own MCP server endpoint by default, so that clients registered dynamically, which cannot list resources themselves, may request access tokens for it. checkOidcClientResource reports whether the client or this setting allowed a resource.
  • The MCP server accepts OAuth access tokens issued by CAS, alongside Basic authentication. It publishes RFC 9728 protected resource metadata that names CAS as the authorization server, challenges unauthenticated clients with both Bearer and Basic, and accepts a token only when it was issued for the MCP endpoint with the mcp:read scope to an application that is still allowed. The MCP_ADMIN role comes from the principal attributes listed in cas.mcp.oauth.required-attributes, resolved for the person when the token is used rather than taken from the attributes released to the client; they match nobody by default, and the audit record of a call names the OAuth client. The AI.mcp-oauth feature toggle turns it off.
  • OpenID Connect clients may identify themselves with client ID metadata documents, as MCP clients do: the client id is an HTTPS URL whose JSON document CAS fetches, checks and registers, refreshes when its cache lifetime ends and removes once unused. Documents are only fetched from public addresses, without redirects and up to 5 KB, and these clients always see a consent screen that names the host of the client id. Turned off by default; enable it with cas.authn.oidc.registration.client-id-metadata-document.enabled=true.
  • The aud of a token introspection response is the audience of the JWT access token: the service audience (or the client ID) and the token’s resources, or the audience requested by a token exchange. It used to be the service URL the token was issued for. Custom OAuth20IntrospectionResponseGenerator implementations now receive the registered service of the client.
  • OAuth/OpenID Connect clients are held to what they registered. They authenticate with their registered method, and only as the client the request names, at the token endpoint and also for pushed authorization, backchannel authentication, revocation and verifiable credentials; an access token no longer authenticates a client. Clients that use mutual TLS must register the subject DN or a subject alternative name of their certificate, unless their client id is exactly the certificate’s SPIFFE ID; a subject DN written as a regular expression must now match the whole subject, as CN=([^,]+),O=Example,C=US does. User profiles keep every value of a multi-valued attribute, and the cas.authn.oauth.csrf-cookie settings are removed since CAS no longer issues that cookie.
  • The page where users approve a device user code now carries an approval token tied to the single sign-on session, and an approval without it is refused, so another site can no longer make a signed-in browser approve a code. Customized protocol/oauth/deviceCodeApproval.html templates must add the hidden approvaltoken input of the default template to their form. The error messages of the page are now defined, under cas.oauth.device.error.*.
  • OAuth/OpenID Connect follow the specifications more closely. Sender-constrained access tokens always require their proof, prompt=login and max_age=0 request parameters always lead to a fresh login and prompt=none to login_required, authorization requests keep all their parameters through login and consent, and refused requests receive the error and challenge the specifications call for instead of a server error. OpenID Connect JWT access tokens no longer fail to sign now and then under load.
  • OAuth/OpenID Connect endpoints no longer send the X-XSS-Protection header, which browsers ignore. Only the X-Requested-With: XMLHttpRequest header now marks a script request that is answered with 401 instead of a redirect to the login; the is_ajax_request header and parameter are no longer recognized.

SAML2

  • SAML2 service provider metadata that cannot be resolved is no longer retried with one-second pauses during the request, and a failure to load it is remembered for cas.authn.saml-idp.metadata.core.failure-cache-expiration instead of contacting the metadata source on every request. Metadata query servers keep one backup per entity, so an entity no longer falls back onto the metadata of another, and metadata stores such as JPA or MongoDB are cached per entity, so providers that share a service definition no longer evict each other’s metadata. Changes to the metadata settings of a service definition take effect on the next request on every node, and checking whether the JPA metadata store is available no longer opens a new connection pool each time.
  • SAML2 identity provider metadata, keys and certificates are fetched again from their storage once cas.authn.saml-idp.metadata.core.cache-expiration has passed, even while in constant use, so a key rotation in a shared metadata store reaches every node.

Attributes & Consent

  • The pattern matching attribute release policy no longer releases the transformation template itself for values that do not match the pattern; such values are dropped, and the attribute is not released when none of its values match, as the inline Groovy transformation already did.
  • The return linked attribute release policy releases the values of the first linked attribute that has a value, as documented; it used to release the last one.

Tickets & Sessions

  • New deployments of CAS, and upgrades to a new CAS version, should always start with a clean JPA ticket registry table: drop the existing table and let CAS create it. Schema updates do not change the type or length of an existing column, and this version changes several of them.
  • With PostgreSQL, the JPA ticket registry stores ticket attributes as jsonb, and session lookups by attribute, as in delegated OpenID Connect and SAML2 logout, can be answered by a GIN index instead of reading every session. The index is not created by CAS: the administrator must create it once after the ticket table is created, with the statement on that page. A table created by an earlier version keeps a json column, on which those lookups fail; start with a clean table or convert the column.
  • The JPA ticket registry stores when each ticket expires, including its idle timeout, and indexes it, and the ticket registry cleaner asks only for tickets whose time has passed, with a full scan at startup and hourly; it used to read and decode every ticket on every run. With MySQL, the registry streams scans through a server-side cursor (useCursorFetch) and leaves single-ticket lookups as they were; the defaults can be overridden with cas.ticket.registry.jpa.properties.
  • Looking up sessions by attribute in the JPA ticket registry no longer fails on MySQL when the caller runs outside a transaction, as delegated OpenID Connect and SAML2 logout do. Updating a ticket encrypts it once instead of twice when ticket encryption is turned on.
  • The JPA ticket registry updates a ticket with a single statement instead of reading the row back first, no longer deletes service tickets twice when a session ends, pages ticket listings in the query instead of reading and skipping the rows before the page, and reads tickets without keeping copies of them for change tracking. Session queries by attribute bind the attribute values as parameters.
  • With MySQL, the JPA ticket registry declares shorter type, principal_id and parent_id columns so that its indexes fit MySQL’s key length limit; until now MySQL refused every one of them. Existing tables need the statements listed on that page. The index on the ticket type alone is gone on all databases.
  • With the stateless ticket registry, device codes keep their requested scopes, so tokens issued for an approved device code carry them; the scopes used to be dropped.
  • The compact form of tickets kept by the stateless ticket registry now carries the resources of OAuth codes, access tokens, refresh tokens, device codes and pushed authorization requests, and the audience of exchanged access tokens; its format version changes: tickets and tokens issued before the upgrade can no longer be read, so users sign in again and clients obtain new tokens.
  • The deprecated Azure CosmosDb ticket registry is removed, along with its settings. Deployments that still use it should switch to another ticket registry.
  • A logout request now looks up its service parameter once for all the steps of the logout flow, where every step, and every single logout protocol in use, used to look it up again. Redirecting logout to the service looks it up once more, and only when cas.logout.follow-service-redirects is turned on. Logout requests that name unknown services, such as those sent by crawlers, cost far less.

Service Registry

  • The JPA service registry reads only the identifier and body of each definition, keeps no entities for reads, and no longer deserializes a definition on reload when its stored body is unchanged. Deleting a service is a single statement, new services are no longer looked up before they are stored, bulk saves flush every batch-size definitions, and the service id and name columns are indexed.
  • The JPA service registry keeps the identifier of a service that carries one, such as an imported definition; a database sequence used to replace it. New services get a random identifier, as with other service registries.
  • A service whose single sign-on participation policy does not set createCookieOnRenewedAuthentication (for example the last-used-time and authentication-date policies) no longer fails the login flow; such a policy behaves like one that leaves the setting undefined, and the single sign-on session is kept when the service does not take part in it.
  • Attribute-based activation criteria for access strategies and attribute release policies match required values against the entire attribute value, like required and rejected attributes; admin no longer activates a policy for sysadmin. Use .*admin.* to match part of a value.
  • Service replication no longer broadcasts every service definition from every node on each reload: a loaded definition is sent only when it differs from the replicated copy, and the replicated copies are kept across reloads instead of being cleared, so nodes started later still receive every definition. A replicated definition that differs from the local one replaces it instead of being listed twice.
  • When several service registries are chained, a service URL that is not cached is matched against the best candidate from every registry by evaluation order, instead of the first registry’s match.
  • The REST service registry no longer publishes a loaded event for every service when services are counted or looked up, and counting services while the registry is unreachable logs the failure and reports zero instead of failing (for example at startup).
  • The REST access strategy calls its endpoint once per access decision, without retries, and waits at most 5 seconds for the response; an endpoint that does not answer in time denies access. It used to retry up to three times on errors and timeouts, holding the login for the duration.
  • Groovy single sign-on participation policies and Groovy activation criteria for access strategies and attribute release resolve their script once, and again only when the script changes or expires from the script cache, instead of resolving its location and expressions on every evaluation.
  • Service replication through Apache Kafka keeps one entry per service definition; an updated definition used to be stored next to its earlier versions.
  • A service definition deleted on one node stays deleted across the cluster with service replication: the deletion marker is kept instead of being removed by the first node that applies it, so nodes that still have the definition remove it rather than sending it back. Deletions now also replicate through Apache Kafka, whose nodes used to drop the marker on arrival.
  • With service replication through Apache Kafka, a node reads the replication topic from the beginning when it starts, so it receives the service definitions that other nodes loaded before it joined; it used to rely on every node sending all definitions again on every reload.
  • With the services cache turned off (cas.service-registry.cache.cache-size set to 0), listing services no longer re-indexes every service it reads, which also made the next service lookup read the whole service registry again.
  • The deprecated Azure CosmosDb service registry is removed, along with its settings. Definitions stored there should be exported and imported into another service registry.

Interface & Accounts

  • The account profile only ends single sign-on sessions, revokes OpenID Connect tokens and removes trusted devices that belong to the signed-in user; it used to act on any session, token or device whose identifier was submitted.
  • Themes other than the default one, including themes chosen per application or per tenant, now inherit cas-theme-custom.properties before falling back to cas-theme-default.properties. Theme files found under the template prefixes now apply regardless of the browser language; they used to be ignored for languages other than English, and the aggregate theme source only honored them for an exact en request.
  • The account profile and account management pages follow the shared card, text and border colors of the theme, and the light Palantir theme follows the theme’s primary and secondary colors.
  • When password management is turned off, the login page no longer links to https://pwd.example.org; the address of an external password recovery page is set with the cas.pm-links.forgot-password.url theme property, and nothing is shown when it is blank.
  • Date fields in the Palantir service wizard open a calendar to pick from: the expiration date, client secret expiration dates, and the start and end of a time-based access strategy, which take the start and the end of the picked day. Values of the access strategy types (remote, HTTP request, time-based and others) and of the proxy and token exchange policies now reach the generated definition; they used to be left out.
  • Generated passwords on the password update form and client secrets generated in Palantir use the browser’s cryptographic random number generator. WebAuthn no longer shows the session token after authentication, and the account unlock page only blocks the context menu on the captcha.
  • Browser storage pages show their error panel when progress display is turned off, instead of leaving a blank page.
  • Labels and messages that were written in English inside templates and scripts (generic success page, logout confirmation, error pages, QR code login, WebAuthn progress, attribute consent, interrupts, delegated profile selection, impersonation, device code approval, account profile and sign-up dialogs) now come from message bundles.
  • Turning on CAS login for Palantir no longer sends other protected endpoints, such as actuator endpoints and the MCP server, to the CAS login page; they challenge for their own credentials again, as API clients expect, and only Palantir redirects to CAS.

Platform & Operations

  • The MCP server can offer tools that change CAS: end the single sign-on sessions of a person with single logout, release throttled logins, turn an application on or off, change a log level, revoke OAuth tokens and consent decisions, and remove trusted devices, one-time password devices and WebAuthn devices. They are turned off by default, are turned on with the AI.mcp-write feature toggle, and require the new MCP_OPERATOR role. With an OAuth access token, that role also requires the mcp:write scope and the principal attributes listed in cas.mcp.oauth.operator-required-attributes, which match nobody by default.

Documentation

  • The SPNEGO settings explain that cas.authn.spnego.properties[0].jcifs-service-password is only used when cas.authn.spnego.system.use-subject-creds-only is true (otherwise the service keys come from a keytab), and that setting both the Kerberos KDC and realm makes the JDK ignore the Kerberos configuration file.

Build & Project

  • A large number of dependencies and libraries have been updated to their latest versions.
  • MariaDB integration tests and functional test scenarios use port 3307, so they can run alongside the MySQL tests on 3306.
  • Browser tests now cover service matching strategies (literal, starts with, full and partial regular expressions), throttled ticket-granting ticket timeouts, per-service service ticket, proxy ticket and proxy-granting ticket expiration policies, single sign-on participation policies (never, last used time, authentication date), per-service security headers, encrypted, pattern matching, linked, environment and Groovy script attribute release policies, the anonymous username provider, multifactor bypass by remote address, request header and credential type, and the REST multifactor trigger (cas.authn.mfa.triggers.rest.url).
  • Browser tests now cover OpenID Connect front-channel logout, refused hybrid and unauthorized response types, encrypted user info and introspection responses, JWT refresh tokens, optional ID token encryption, token revocation with its cascade from refresh tokens to access tokens, WebAuthn signature counters, user verification and attestation, and Google Authenticator replay protection with custom code length, time step and window.
  • Browser tests now sign in with SPNEGO against a real Kerberos KDC: the browser presents a Kerberos ticket and is signed in without a password, with and without cas.authn.spnego.principal-with-domain-name, and falls back to the login form when it has no ticket.

General

  • The SAML2 identity provider, OAuth/OpenID Connect, UMA, Heimdall, JWT authentication and Duo Security no longer depend on pac4j, which remains only in delegated authentication and the features that hand off to it, such as passwordless authentication and ADFS integration. They are built on Spring Security and CAS components and keep their session state in a CAS session store, in the http session, in browser storage or in the ticket registry as configured. Customizations, Groovy scripts and session store beans that use pac4j types must be updated, and authentication handler names recorded in audit logs no longer carry pac4j class names. OAuth/OpenID Connect sign-ins and pushed authorization requests that are under way during the upgrade must start again. SAML2 requests passed on to SAML2 identity providers keep their forced and passive authentication, authentication contexts and scoping.
  • When the SAML2 identity provider or Duo Security keep their session state in browser storage, the browser receives only the state of that flow rather than every attribute of the http session, and the state expires with the lifetime of transient session tickets (cas.ticket.tst.time-to-kill-in-seconds). A state that has expired or belongs to another flow restores nothing; sign-ins under way during the upgrade must start again.
  • CSRF protection is configured once for all modules, so OpenID Connect and WebAuthn no longer override each other’s settings, and the backchannel authentication verification page is now protected. A custom CSRF token repository is defined once, as the casCsrfTokenRepository bean.

Test Release Candidates Early

CAS releases are strictly time-based, and a GA release is a tag and nothing more. Trying each release candidate and the snapshots that follow it is the best way to gain confidence in an upgrade.
